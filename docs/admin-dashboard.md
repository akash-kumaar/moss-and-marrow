# Owner dashboard setup and operations

The owner dashboard is served at /admin. APIs under /api/v1/admin require a server-stored owner session and enforce role checks. Mutations require the session's CSRF token. Cookies are HttpOnly, SameSite Strict, expire after eight hours and require HTTPS in production. Never disable Secure to serve owner credentials over public HTTP. No public owner registration route exists.

Provision an owner through an approved secure host session using the backend command npm run admin:bootstrap. Provide MONGODB_URI, ADMIN_BOOTSTRAP_EMAIL and ADMIN_BOOTSTRAP_PASSWORD through the secret environment. The bootstrap password must have at least 16 characters. Passwords use salted scrypt hashes. Duplicate owner emails fail without changing the original account. Remove bootstrap credentials after provisioning. Do not place passwords in command arguments, logs or Git. The existing deployment does not automatically create an owner or pass bootstrap credentials.

Owner access includes filtered, paginated reservations, CSV exports capped at 5,000 records, customer history grouped by normalized email, read-only branch summaries, enquiries, menu edits and explainable booking integrity signals. Integrity flags are review leads. No flagged records are deleted, hidden or cancelled. MongoDB windows calculate repeated-email and minute-burst signals across the collection before applying filters. Queries have the existing five-second server limit. Benchmark these windows on a restored production copy before rollout.

Reservation calendar fields are interpreted as UTC calendar dates, with today determined in Asia/Kolkata. Overview date filters apply to booking dates. Customer counts represent unique normalized email strings and may not equal unique people. Today includes active pending/confirmed bookings. Completed/cancelled bookings cannot be reactivated through the dashboard because their seating may have been reused. Staff can create a new reservation through the capacity-checked form. Status changes use an optimistic condition to avoid overwriting a concurrent change.

Production rollout requires current EC2 identity, private recoverable backup, compatible indexes, verified running digests and green release checks. Verify HTTPS and owner provisioning before exposing login. Session metadata and owner records live in MongoDB and are included in backups. The new enquiry status defaults to pending and legacy records without status remain pending for filtering. Public APIs remain separate from owner management.

Known remaining work: quick week/month filters, reservation sort controls, integrity CSV exports and severity filters, detailed per-branch seating/status reports, and full browser interaction testing. Frontend statistics are real database aggregates. No email or marketing delivery is implemented.

## Demo login
Admin login uses email and password only. Provision each account privately using admin:bootstrap; no public registration exists. Authenticator codes are not required. Never reuse a real personal password for demo accounts.

Production booking/enquiry submissions additionally reject reserved/example domains and domains without a usable MX record. DNS failures return a retryable error. This checks the domain, not mailbox ownership: email OTP requires a transactional mail provider, which is not configured. Real names, phone ownership and intent cannot be guaranteed. Existing IP rate limits, request size limits and capacity/idempotency checks remain active. Turnstile remains optional and needs its existing server/site configuration. These controls do not prevent distributed denial of service; upstream protection is still necessary for that threat.
